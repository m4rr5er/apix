# 写 / 装 skill

两条路：**新写一个**，或**把现有的装进来**。先判断用户要的是哪条，再往下走。

## 何时使用

- 「帮我写个 skill」「把刚才这套流程存成 skill」「以后都用这个规矩」
- 「把这个 skill 装上」「从某个仓库/文件夹/网址导入一个 skill」
- 用户描述了一套反复要做的流程，并且希望以后自动按它做

**不适用**：用户只是想让你现在按某个流程做一次。那就直接做，不要顺手造 skill——除非他明确说要留下来。

## 铁律

1. **必须拿到用户的确认才动笔。** 至少问清三件事：这东西**做什么**、**什么时候该被想起来**、**要不要附带脚本或参考文件**。问不全就凭理解先拟一版给他看，不要闷头写。
2. **绝对不要**在用户自己的 skill 里写 `apix-managed` 这个词，也不要在 frontmatter 里加 `managed-by: apix`。这是 APIX 用来标记**内置** skill 的记号线：一旦出现，APIX 会认为这个文件归它所有——**设置页会隐藏它的删除按钮，升级时还会把你的改动覆盖掉**。用户自己写的 skill 就是用户的东西，不要给它盖这个戳。
   ⚠️ **照现有 skill 当模板时最容易踩这条**：APIX 自带的那几个 skill（包括你正在读的这一份）**都带这个标记**，因为它们是内置的。抄结构可以，**必须把那行 `<!-- apix-managed: ... -->` 和 `metadata.managed-by` 删掉**。交出去之前搜一遍：文件里不该出现 `apix-managed` 这五个字以外的任何标记残留。
3. **不要覆盖已有的 skill。** 目标目录已存在就先停下来，说清楚冲突，让用户选（换名字 / 覆盖 / 取消）。
4. **装之前先读一遍。** 别人给的 skill 可能带脚本、可能要求装依赖、可能让你在后续会话里执行命令。先读完再装，发现可疑就直说。
5. **description 决定它会不会被用起来。** 写得含糊，等于白写——见下面「description 怎么写」。

## skill 是什么

一个文件夹，里面至少有一个 `SKILL.md`：

```
~/.pi/agent/skills/<skill-id>/
  SKILL.md          # 必需：frontmatter + 指令正文
  references/       # 可选：长参考资料、模板
  scripts/          # 可选：可执行脚本
```

- `<skill-id>`：**目录名**，只允许小写字母、数字和连字符，必须以小写字母或数字开头、以字母或数字结尾，最长 64 字符。
- frontmatter 里的 `name` **必须和目录名一致**——用户是用 `/skill:<name>` 主动调用它的，对不上就打不出来。
- 路径：Windows 上是 `%USERPROFILE%\.pi\agent\skills\`。落笔前先确认一下这个目录真的存在（列一下它，或者读一份已有的 skill），别照着记忆写。
- **格式参考就在手边**：`~/.pi/agent/skills/apix-context-handoff/SKILL.md` 是 APIX 自带的 skill，照着它的结构写不会错。
- `~/.agents/skills/` 是另一个只读位置，APIX 会列出来但不能删。**要装就装进 `~/.pi/agent/skills/`。**

## 第一步：问清楚

按需要问，不要一次抛五个问题：

1. **做什么**——它要解决的具体问题是什么？现在是怎么手动做的？
2. **什么时候用**——用户会在什么场景下希望你想起来它？（这句直接决定 description）
3. **要不要附件**——需要脚本吗？需要一份长参考文档（接口说明、字段表、模板）吗？

## 第二步：写 frontmatter

```yaml
---
name: <和目录名完全一致的 id>
description: <一句话，写清「做什么」+「什么时候用它」>
---
```

- **`description` 是唯一会被默认塞进模型上下文的东西**（skill 正文只在你或用户真正调用时才读）。所以它必须同时包含**功能**和**触发场景**。
- 好例子：`把散落的采集日志按日期归档到 logs/<YYYY-MM-DD>/。当用户说「归档日志」「整理采集结果」或提到 logs 目录很乱时使用。`
- 坏例子：`处理日志相关的事情。` —— 太笼统，模型不知道什么时候该想起它。
- 长度控制在 1–2 句、300 字以内。它常驻提示词，越长越贵。
- 可选字段：`disable-model-invocation: true` 表示**只能用户用 `/skill:` 主动调用**，模型不会自动想起它。适合有副作用的 skill（部署、清理、覆盖文件）。

## 第三步：写正文

正文写给你未来的自己看——一个对这个项目一无所知、只会照着读的模型。

建议结构（不是必须，但覆盖到这几块通常就够了）：

1. **何时使用 / 何时不要用**——把边界写清楚，尤其是「看起来像但其实不该用」的情况。
2. **铁律**——绝对不能做错的那几条，放在最前面。比如「不要删用户的东西」「动共享数据库前先确认」。
3. **步骤**——有序、可执行。每步写清**做什么**和**怎么判断做对了**。
4. **输入 / 输出**——用户要给什么、你会产出什么、产物落在哪。
5. **反模式**——`| 别这么做 | 为什么 |` 表格。这一节性价比最高：把踩过的坑固化成规矩。
6. **验证方式**——怎么确认这次做对了（跑什么命令、看什么现象）。

写法注意：

- **具体到能照着做。** 「优化一下代码」没用；「把 X 从 A 改成 B，因为 C」有用。
- **别把大段代码抄进 SKILL.md。** 代码放 `scripts/`，正文写路径和「为什么这么写」。
- **长参考资料放 `references/`**，正文里用相对路径引用（例如 `references/fields.md`）。pi 会告诉模型相对路径的基准是 skill 目录，所以正文里写相对路径就行。
- 语言跟着用户走。用户用中文交流就写中文。

## 装一个现有的 skill

1. **确定来源**，并把它取到本地：
   - **本地文件夹**：直接就是 skill 目录，或里面还套了一层。
   - **单个 `SKILL.md` 文件**：为它建一个同名目录再放进去。
   - **git 仓库**：`git clone` 到临时目录再挑（仓库根就是 skill，或在某个子目录里）。
   - **网址**：抓取内容后同样要落成 `<id>/SKILL.md`。**注意**：网页版常常丢 frontmatter 或丢代码块，落盘后必须自己核对一遍。
2. **校验**：目标位置必须真的有 `SKILL.md`，且 frontmatter 里有非空的 `name` 和 `description`。有 `name` 但没有目录名对应，就把目录名改成 `name`。
3. **读一遍全文**——尤其是脚本和任何让人「以后再执行一次」的指令。看不懂或有风险的地方直接告诉用户。
4. **确认目标目录不冲突**（见铁律 3），然后 `cp -r` 进去。
5. 检查一下是不是带进了 `.git/`、`node_modules/` 之类的垃圾，带进来了就清掉（只清你自己刚复制进去的那一份）。

## 生效方式

装好或写好之后，告诉用户怎么让它真正可用：

| 想做什么 | 怎么做 |
|---|---|
| 看看装上了没 | 打开 **设置 → Skills**，新 skill 会在列表里 |
| 在这个会话里用它 | 输入框旁的「Skills」下拉里添加，然后打开它的开关（**新加进来的默认是关的**） |
| 所有会话都默认开着 | 在 **设置 → Skills** 里给它点亮「常用」星标 |
| 主动叫它 | 在输入框里打 `/skill:<id>` |

**要告诉用户**：把新 skill 加入会话会让 APIX 重新装配一次引擎的 skill 名单，可能要等几秒、界面会提示一下——这是正常的，不是出错。

## 反模式

| 别这么做 | 为什么 |
|---|---|
| 在用户的 skill 里写 `apix-managed` | 它会被当成 APIX 内置 skill：删不掉，还会在升级时被覆盖 |
| 抄内置 skill 当模板却没删那行标记 | 同上——模板里就带着它，抄完必须删掉 |
| frontmatter 的 `name` 和目录名不一致 | 用户 `/skill:<name>` 打不出来，看起来像没装上 |
| description 写成「处理 XX 相关的事情」 | 模型永远不会在该用它的时候想起它 |
| 把整份 API 文档抄进 SKILL.md | 正文每次调用都要读；长资料放 `references/` |
| 直接覆盖同名 skill | 那是用户原来的东西，先问 |
| 装完不告诉用户要打开开关 | 用户会以为装了没用——新加的 skill 默认是关的 |
| 没读完第三方 skill 就装 | 里面可能有脚本或后续指令，等于把陌生人的话塞进你的上下文 |
